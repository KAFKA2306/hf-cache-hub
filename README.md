# hf-cache-hub

[![CI](https://github.com/KAFKA2306/hf-cache-hub/actions/workflows/pinned-cache.yml/badge.svg)](https://github.com/KAFKA2306/hf-cache-hub/actions/workflows/pinned-cache.yml)

Hugging Face modelをrevision固定で共有cacheへ配置し、複数projectから同一snapshotを参照するための小さなbootstrap utilityです。生成artifactについては、Gitにlarge binaryを置かず、Storage Bucket上のobjectをhashとprovenanceで宣言するcontractも提供します。

## 他のrepositoryから使う

このrepositoryは、他のGit repositoryがPLY、checkpoint、video、dataset等のlarge artifactをGit historyへ入れずに扱うための共通基盤として使えます。

基本原則は次の分離です。

```text
project repository
  code + config + thin artifact manifest
                 │
                 ▼
            hf-cache-hub
        validate / publish / resolve
          │                    │
          ▼                    ▼
Hugging Face Storage Bucket   shared local cache
mutable remote bytes          $HF_HOME/artifacts/sha256/...
```

各project repositoryはHugging Face upload/download処理を独自実装せず、artifactの識別情報とprovenanceだけを保持して、このrepositoryのCLIを呼びます。Storage Bucketのpathはmutableなので、それだけをartifact identityとして扱いません。`size_bytes`、SHA-256、生成元repositoryのexact Git commitをmanifestに固定します。

### 1. hf-cache-hubを共通配置する

例:

```bash
git clone https://github.com/KAFKA2306/hf-cache-hub.git ~/src/hf-cache-hub
export HF_CACHE_HUB_ROOT="$HOME/src/hf-cache-hub"
export HF_HOME="$HOME/hf-cache"
```

artifact機能だけを利用するPython環境には、現在少なくともPyYAMLと`huggingface_hub`が必要です。

```bash
python -m pip install "PyYAML>=6.0,<7" "huggingface-hub>=1.0,<2"
```

`HF_CACHE_HUB_ROOT` は説明用のshell variableです。project固有のwrapperを作る場合も、upload/downloadロジック自体は複製せず、このrepositoryのscriptへ委譲してください。

### 2. project側にはthin manifestだけを置く

project repositoryに例えば `artifacts.yaml` を置きます。large binary本体はGit管理しません。

```yaml
schema_version: 1
artifacts:
  - id: example/splat
    kind: gaussian-splat
    format: ply
    storage:
      type: huggingface-bucket
      bucket: KAFKA2306/artifacts
      path: gaussian/example/splat.ply
    size_bytes: 123456
    sha256: 0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
    provenance:
      repository: KAFKA2306/AutoPhotogrammetry
      revision: 0123456789abcdef0123456789abcdef01234567
      source_path: output/example/export/splat.ply
```

検証:

```bash
python "$HF_CACHE_HUB_ROOT/scripts/artifact_manager.py" \
  --manifest ./artifacts.yaml \
  validate
```

### 3. producer repositoryからpublishする

producerはartifact生成後にlocal fileのsize/SHA-256とmanifestを一致させたうえで、共通publisherを呼びます。

```bash
python "$HF_CACHE_HUB_ROOT/scripts/artifact_manager.py" \
  --manifest ./artifacts.yaml \
  publish ./output/splat.ply \
  --id example/splat
```

publishはlocal size/SHA-256を先に検証し、Storage Bucketへuploadした後、remote objectをreadbackして再度size/SHA-256を検証します。完全一致した場合だけ `status: PUBLISHED` を返します。失敗時にlocal artifactは削除しません。

remoteへ書かずに確認する場合:

```bash
python "$HF_CACHE_HUB_ROOT/scripts/artifact_manager.py" \
  --manifest ./artifacts.yaml \
  publish ./output/splat.ply \
  --id example/splat \
  --dry-run
```

producer repositoryが持つ責務は、生成、manifest/provenance作成、共通publisher呼び出しまでです。Hugging Face upload/readback処理をproject側へ複製しません。

### 4. consumer repositoryからresolveする

まずshared cacheの状態だけ確認できます。この操作はremote downloadを行いません。

```bash
python "$HF_CACHE_HUB_ROOT/scripts/artifact_cache.py" \
  plan \
  --manifest ./artifacts.yaml
```

結果はartifactごとに `HIT`、`MISS`、`CORRUPT` を返します。

artifactを取得する場合:

```bash
python "$HF_CACHE_HUB_ROOT/scripts/artifact_cache.py" \
  resolve \
  --manifest ./artifacts.yaml \
  --id example/splat
```

verified objectは既定で次へ保存されます。

```text
$HF_HOME/artifacts/sha256/<sha256>/<filename>
```

同じSHA-256を要求する別repositoryは同じlocal objectを再利用します。cache hit時もsize/SHA-256を再検証します。壊れたcache objectやpartial downloadは完成artifactとして再利用しません。

project内の既存pathへmaterializeする場合:

```bash
python "$HF_CACHE_HUB_ROOT/scripts/artifact_cache.py" \
  resolve \
  --manifest ./artifacts.yaml \
  --id example/splat \
  --materialize ./Library/MyProject/GaussianSources/example.ply
```

既定はshared cache objectへのsymlinkです。symlinkを作れない環境で明示的にcopyを許可する場合だけ `--copy-fallback` を追加します。

### 5. project repositoryで保持するもの / 保持しないもの

保持するもの:

- source code
- small config
- `artifacts.yaml` 等のthin manifest
- `size_bytes`
- SHA-256
- exact Git revisionとrun/source provenance
- 必要ならignored materialization path

保持しないもの:

- PLY、checkpoint、video等のlarge generated bytes
- Hugging Face token、password、API key等のcredential
- projectごとに複製したStorage Bucket upload/download実装
- mutableなBucket pathだけを根拠にしたartifact identity

### 6. producerとconsumerの成功条件

producerは生成成功とremote publish成功を別statusとして扱ってください。artifact生成が成功しても、uploadまたはremote readbackが失敗した場合は `PUBLISHED` とみなしません。local artifactを残せば、trainingや生成処理をやり直さずpublishだけ再実行できます。

consumerはresolverが `status: READY` を返し、manifestと一致する `size_bytes` / SHA-256のcache objectを得た場合だけmaterialization成功と扱ってください。既存のconsumer側hash検証がある場合は削除せず、最終materialization後にも検証を残してください。

### 7. migration時の原則

既存repositoryを移行するときは、先にremote artifactのpublish/readbackを確認し、その後でconsumerの正準sourceを切り替えます。未publishのartifactに先回りしてGitHub raw等の既存sourceを削除すると、clean cloneから復元できなくなるためです。

`KAFKA2306/AutoPhotogrammetry` はproducer integration、`KAFKA2306/vrmine` はconsumer integrationの実装例です。100 MiB synthetic artifactを2つのclean consumer repositoryで共有し、1回目のresolve後に2 repository目がshared cacheを再利用するcontract testもあります。実Storage Bucketを含むacceptanceの証拠境界は [`docs/artifact-storage-acceptance.md`](docs/artifact-storage-acceptance.md) を参照してください。

## Shared cache

```bash
export HF_HOME="$HOME/hf-cache"
export HF_HUB_CACHE="$HF_HOME/hub"
```

## Model contract

`models.yaml` では `org`、`repo`、full 40-character `revision`、`purpose`、`access`、`license_url`、`model_card_url` を宣言します。tokenやsecretはmanifestへ書きません。

```yaml
models:
  - org: Tongyi-MAI
    repo: Z-Image-Turbo
    revision: f332072aa78be7aecdf3ee76d5c247082da564a6
    purpose: image-generation
    access: PUBLIC
    license_url: https://www.apache.org/licenses/LICENSE-2.0
    model_card_url: https://huggingface.co/Tongyi-MAI/Z-Image-Turbo
```

## Artifact contract

`artifacts.yaml` は生成済みlarge artifactの実体を保持しません。Storage Bucket上のobjectを `bucket + path` で指し、mutableなremote locationとは別に `size_bytes`、SHA-256、生成元repositoryのexact Git commitを保持します。

```yaml
schema_version: 1
artifacts:
  - id: example/splat
    kind: gaussian-splat
    format: ply
    storage:
      type: huggingface-bucket
      bucket: KAFKA2306/artifacts
      path: gaussian/example/splat.ply
    size_bytes: 123456
    sha256: 0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
    provenance:
      repository: KAFKA2306/AutoPhotogrammetry
      revision: 0123456789abcdef0123456789abcdef01234567
      source_path: output/example/export/splat.ply
```

検証:

```bash
python scripts/artifact_manager.py validate
```

schemaはunknown fieldを拒否し、`sha256`、`size_bytes`、exact 40-character provenance revision、`source_path`または`run_id`を必須にします。token、secret、password、credential、API keyに相当するfieldはmanifestのどの階層でも拒否します。`storage.bucket` と `storage.path` は `hf://buckets/<namespace>/<bucket>/<path>` に一意に解決されます。

## Artifact publish

manifestに宣言済みのlocal fileをStorage Bucketへpublishする前に、local sizeとSHA-256を検証します。upload後は同じremote objectを一時fileへreadbackし、sizeとSHA-256が完全一致した場合だけ `PUBLISHED` を返します。

```bash
python scripts/artifact_manager.py publish ./output/splat.ply --id example/splat
```

remoteへ書かず計画だけ確認:

```bash
python scripts/artifact_manager.py publish ./output/splat.ply --id example/splat --dry-run
```

publish/readbackにはHugging Face公式Python APIの `batch_bucket_files` と `download_bucket_files` を使用します。認証情報は引数・manifest・result JSONへ保存せず、Hugging Faceの既存credential/OIDC経路に委ねます。認証・upload・readback・hash検証のいずれかが失敗すれば非0終了し、readback不一致時はremote objectをbest effortで削除します。local artifactは自動削除しません。

Hugging Face公式ではStorage BucketsはGit historyを持たないmutable object storageで、checkpoint、logs、intermediate artifacts等のlarge working data向けです。versioned model/dataset repositoryとは責務を分離します。

- https://huggingface.co/docs/hub/storage-buckets
- https://huggingface.co/docs/huggingface_hub/guides/buckets

## Plan and sync

Download前のcache状態を確認:

```bash
task hf:plan
```

指定revisionをdownloadし、そのrevisionのsnapshotだけをlinkして `cache-manifest.json` を生成:

```bash
task hf:sync
```

生成link:

```text
models/REPO -> $HF_HUB_CACHE/models--ORG--REPO/snapshots/<pinned-commit>
```

`hf:sync` はsnapshotのmtimeから「最新」を推測しません。download APIが返したsnapshot名が指定revisionと一致しなければfail closedします。

## Cache management

```bash
task hf:ls
task hf:prune
```

gated/private repositoryは顧客自身のHugging Face credentialを使用します。credentialが取得できなければsyncしません。license URL/model card URLは確認先として保持するだけで、商用利用可否を自動判定しません。

チーム導入PoCの境界と2-project demo手順は [`docs/services/team-cache-bootstrap.md`](docs/services/team-cache-bootstrap.md) を参照してください。
